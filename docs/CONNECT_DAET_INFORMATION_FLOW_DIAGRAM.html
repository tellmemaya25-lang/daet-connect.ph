Each role communicates with the system; the platform validates, records, and routes authorized updates. Short arrow labels point to the detailed payloads in each role box.

Key role-to-role handoffs

The people may communicate with each other, but the application mediates platform data and enforces who can see it.

OPERATOR → SYSTEM → GUIDE

Assignment and guest roster

The operator assigns a guide to a booking. CONNECT-DAET saves the assignment and sends a New tour assigned alert to the guide (and a guide-assigned update to the tourist). The guide then opens the protected roster to fetch the guest list; the manifest is not sent as an unrestricted direct file.

TOURIST → SYSTEM ↔ PAYMONGO

Payment information

The tourist chooses a payment route and starts checkout. Card details are entered in PayMongo's hosted flow, not stored by CONNECT-DAET. The system accepts a signed, verified payment event before updating status. For manual payment, receipt proof is stored privately and reviewed by the operator.

TOURIST ↔ SYSTEM ↔ OPERATOR / GUIDE

Messages and trip updates

In-app conversations carry tourist–operator or tourist–guide messages. The system routes the message to the permitted participants and may create an in-app or configured push/email notification. Booking, payment, guide assignment, check-in, and call-off updates use the same role-aware path.

SYSTEM → ADMIN

Operational tourism analytics

The current Admin dashboard reports tourist check-ins, bookings and confirmed travelers, revenue received, cancellation rate, revenue by operator, top packages, top attractions in saved trip plans, ratings, accreditation queues, feedback, and audit records.

Accuracy notes

Admin reports are analytics, not a separate formal assessmentThe application currently provides operational tourism analytics. It does not label or generate a standalone “Tourism Impact Assessment Report”; this diagram avoids implying that it does.
Trip planning is grounded in Daet dataThe planner takes dates/group/origin from the trip questions and interests/budget/pace from the tourist's request. Database-backed rules determine stops, times, and prices. Gemini and Maps/Routes are optional; fallback planning and route estimates remain available.
Check-in is validated by the systemA signed ticket or roster action is checked against the caller's role, guide assignment, tour date, booking, and payment status. The system returns accepted/already/rejected status and records authorized check-ins.
Live-tour privacyTourist location sharing is opt-in; guide location is limited to the live-tour window. Trip mode uses town-level location. Only the latest position is retained, and the session lifecycle clears live-position and flare records.
