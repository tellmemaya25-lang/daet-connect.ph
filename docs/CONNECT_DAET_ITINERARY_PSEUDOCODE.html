CONNECT-Daet Itinerary Planner

A simple pseudocode guide to how a Tourist's request becomes an itinerary in the current system.

Important: Gemini is optional and helps read the Tourist's preferences. The system's rule-based planner builds the actual schedule from listed places and data. It does not ask Gemini to invent a complete itinerary in JSON and save it automatically.

Sample request and response from testing

The current endpoint is POST /api/assistant. Its request uses messages and optional trip context; the signed-in user comes from the server session, not a client-supplied tourist_id. Daet is the planner's destination, dates and traveler details belong in context, and interests and budget can be read from the message.

The example endpoint /api/generate-itinerary and fields such as destination, duration_days, budget_php, preferences, itinerary_id, and total_estimated_cost are not the current contract. The planner streams NDJSON events with Content-Type: application/x-ndjson; charset=utf-8 rather than returning one {status, data} JSON object; the itinerary is carried in a t: "itinerary" event under itinerary.plan.days[].blocks, not a schedule field. The response events are shown as a formatted JSON array for readability; expand the raw stream to see the actual line-by-line wire format.

System details shown in this logic

      
    
        
  • The planner asks for missing trip details such as dates or a sample-plan choice, traveler counts and child ages, and where the Tourist is travelling from.
    • 
        
  • Gemini may interpret interests, budget, and pace from the message. If Gemini is unavailable, the basic text parser can still read preferences.
    • 
        
  • The rule engine uses database listings to choose places and calculate the schedule. It uses listed opening hours, entrance fees, group size, and travel estimates; interests guide selection but can still result in stops from other available categories.
    • 
        
  • Bookable tour packages and listed fares are added when available. Missing tour or fare data does not stop the itinerary from being shown.
    • 
        
  • Changing pace can regenerate the plan. Changing the getting-around choice changes travel labels; travel-time values remain road estimates.
    • 
        
  • A no-date sample uses stand-in dates. The Tourist must choose real dates before saving it.
    • 
        
  • Saving is a separate user action and requires sign-in. Offline saving may happen automatically after a saved itinerary is opened; it is not a setting the Tourist turns on.
